# 未读与回复义务分流

## 原因与行为

原先私聊未读在采集时会先创建 `triage=pending` 的待回复。群聊的 AI 提示词虽要求识别本人义务，但新建回复记录没有与待办相同的程序限制，因此普通未读群消息可能被误建为待回复。

本次调整：

- 私聊未读先保留来源、收件箱快照和分析队列，采集不再预先创建回复记录。AI 明确需要回复后才登记；私聊具体业务事项继续只生成待办。
- 群聊新建待回复与待办共用收录边界：需要结构化 @本人或 @全员，并由 AI 判断存在对应义务。普通群未读、问题或 @他人不会仅凭 `needsReply=true` 建档。
- 既有回复的后续引用、本人真实答复核对、人工状态保护与忙碌自动回复保持现有行为。
- 首页独立回复、关联回复与待回复页提供“已查阅”。它调用原有人工阶段更新，将本条标为“不需回复”，保留记录、设置人工保护；不发送、不修改云之家未读，也不完成关联待办。
- 既有误判记录不批量清理，可直接在首页逐条点“已查阅”，也可在待回复页处理；新规则用于后续建档。

- 全部后端回归与页面首屏渲染通过；首次组合回归的新增界面测试存在同名选项查询歧义，修正查询后完整重跑界面测试：34 个文件、555 项通过。

- 上述模型、CLI与收件箱验证采用隔离合成数据；没有发送真实企业消息，也没有修改真实会话的已读状态。
- 已通过日常 DeepSeek Harness 的插件管理停用并启用本地链接插件，恢复“待回复”页面；实际宿主已显示新说明与“已查阅”按钮及其悬停说明。未点击任何真实消息的阶段按钮，未批量处理旧记录。真实模型对后续新增消息的持续识别效果仍需在日常使用中观察。
