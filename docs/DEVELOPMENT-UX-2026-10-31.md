# 研发工作台页面与流程重构

本次将原 Agent 中心按实际用途重新组织，目标是让用户从工作项进入开发流程，无需先理解 CLI 路径、Profile 或 JSON 参数。

## 页面与功能归属

- **研发任务**：保留顶部第二个一级入口。首页显示任务、状态筛选、编号/标题/会话检索，以及所选任务的下一步操作。无任务时直接引导开始，不展示全零统计。
- **智能办公**：独立一级入口，承接回复草稿、日报/周报、待办方案和真实后台作业；通用历史记录为这里的“执行记录”。待办方案和快捷面板深链同步改到此处。
- **工作项执行记录**：归属于具体研发任务，在“任务信息”按需读取 Linky 记录。Linky 原生触发的适配器记录保留独立来源标识，不冒充已通过人工审查。
- **工作空间**：新建任务时就地选择；切换空间或类型自动清除旧选择并读取当前工作项，不占独立页签。
- **研发设置**：轻量弹窗。常规只展示工程验证与独立工作区位置；CLI 路径/Profile 和 Linky 发起任务的适配参数位于高级区。

## 主流程

1. 自动发现本机 Linky CLI 和桌面 Profile，用现有认证只读检查账号与工作空间。只发现可执行文件和配置名，不读取、复制或展示凭据。
2. 点击“新建研发任务”：从本人工作项选择，或按编号查询；下一步确认本地工程、Linky 执行角色和测试命令。
3. 测试命令优先复用保存配置，否则读取工程 package.json 的 test/check 脚本，结合锁文件识别 pnpm/yarn/npm。用户确认后才保存；不会在检测时执行项目脚本。命令编辑器转为 argv，拒绝 shell 管道/串联。
4. 创建独立工作区和 Harness 专属会话后展示任务；“开始开发流程”仍需显式点击。
5. 分析、开发、真实测试、独立自动审查连续执行。详情突出当前阶段、累计进度、剩余阶段和暂停原因；差异/验证、会话过程、任务信息分区查看。
6. 人工批准与回写是两个独立动作，批准不会自动回写。回写评论不代表代码已提交、发布或业务状态已关闭。

## 异常与升级体验

- 未安装：直接提示安装，提供 Linky 官方入口和客户端命令行工具安装位置，安装后可重新检测。
- 登录失效：提示回 Linky 客户端重新登录；权限/网络失败单独呈现，保留已有任务可查看。
- 已保存的显式路径无效时不静默换账号，可在高级区选择其他检测到的安装。
- `linky login/setup` 可能附带订阅工作空间等副作用，因此不会自动执行；本次也不启动 daemon 或扩大订阅范围。
- 新客户端配旧宿主：HTTP 404 或旧宿主不识别检测动作时给出组件重载说明，并禁用执行入口。
- 测试脚本识别仅覆盖 Node 项目；其他工程可填写真实测试命令，未配置测试可先准备和开发，到测试阶段暂停等待补充。已有任务可在设置中补充。

## 进入页面自动刷新

进入或切回研发任务即重新查询；窗口恢复前台、文档恢复可见，以及宿主重新显示工作台时也自动刷新工作项、选中详情和研发状态。初次可见观察不重复请求，连续前台事件短时间合并，同条件仍在途的列表请求复用，旧空间或旧选中项的回包不能覆盖当前详情。刷新不会自动执行开发。

同一工作台会话内按账号配置保留空间、类型、完成开关、状态筛选、搜索与选中项；重新进入时读取新的业务数据，保留当前上下文。准备工程弹窗中的输入不会因前台刷新重置。

## 普通目录开发与可选 Git

默认工作方式改为“直接在所选目录开发（无需 Git）”。可以从已有本地工程选择，或在确认弹窗中用系统目录选择器/本地路径输入关联新的普通目录；后续 Host 仅接收保存后的工程别名。普通目录检查只要求目录有效、可读写，不调用 Git；Git 不可用、未初始化或未有提交不会因此阻挡目录模式。

“Git 独立工作区”为可选模式，明确选择后才检查 Git 仓库与 HEAD 并创建隔离分支。旧任务未标模式的仍按原 Git 流程处理。两种模式均不自动初始化仓库、提交、推送或发布，用户可后续决定是否使用 Git。放开 Git 不代表放开操作系统文件访问权限。

普通目录在准备时将现有文件基线保存在 development/directory-baselines（本地0600），不会写入所选源码目录。后续对比新增/删除/修改与权限、符号链接目标，基于全部可审查文件内容哈希绑定人工批准。链接仅记录目标、不跟随读取；原始基线丢失后不能以修改后的内容重建冒充原始差异。同一或相互包含的目录不允许并行执行两个研发任务。源码扫描忽略 VCS 元数据、依赖、IDE 与常见框架缓存（.git/.hg/.svn/node_modules/.venv/venv/__pycache__/.idea/.vscode/.next/.nuxt/.DS_Store）；上限10000个条目/64MB，审查变更上限200文件/512KB。请随 development 整目录备份文件基线。

测试命令是工程的验证方式，可在开发前后补充。未配置时允许先准备、分析、开发，到测试阶段再暂停；不会把未执行的测试标为通过。补充命令后继续原工作区/原会话。普通目录和 Git 目录都保留真实测试、独立自动审查及人工审查。

## 工作方式自动识别

工程确认不再提供工作方式下拉。选择目录后自动检查并展示结果，准备任务前再次检查：可用、有提交、状态干净且 Git 元数据可写的仓库根目录创建独立工作区；普通目录、Git 不可用、没有提交、已有未提交内容、仓库子目录或 Git 元数据不可写时直接使用所选目录。这样保留用户当前修改和所选目录范围。目录读写权限仍然是必要条件。

## 原生 Harness 工作区与研发会话归属

原实现仅传 cwd 创建会话，没有登记到 Harness 工作区，所以新任务出现在“未分组”。现在先通过宿主 workspaceRegistry.create 按开发目录的真实路径创建或复用原生工作区，再以 workspaceId 创建持久会话；不同时传 cwd，不传可复用的空会话 ID。目录别名与软链接合并为同一原生工作区，已有自定义分组名保持不变。

同一个实际开发目录下，不同工作项分别创建独立开发会话；同一工作项再次打开或继续时保留原会话。独立审查创建另一条会话并归入相同工作区。Git worktree 有不同的实际目录，因此分别归组，不与源工程目录混淆。

旧任务在读取详情、再次选择或继续时补齐原生分组归属，不重建会话，不发送模型请求。任务信息显示 Harness 工作区与开发目录；关联失败时仍可读取任务和原会话，显示明确原因。宿主不支持原生工作区时不再静默创建未分组会话。原生创建成功但关联失败时保留返回的会话 ID，重试仅修复归属。

验证：pnpm build、pnpm check、完整 pnpm test 通过（31个界面文件426项测试），其中研发界面33项、研发集成46个场景、CLI适配传输8个场景。新增场景覆盖同目录多会话、软链接去重、旧开发与审查会话补归属、保留自定义名称、宿主能力缺失、关联失败重试不重复创建。证据见 .tmp/development-native-workspace/。
