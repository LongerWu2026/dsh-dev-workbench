# AI 指令快速执行技术方案

> 阶段记录说明：本文件保留指令执行及数据管理的早期设计。导入与自动备份等功能已发生演进，当前实现和缺口以项目说明为准。 [当前项目架构与功能说明](PROJECT-ARCHITECTURE-AND-FEATURES.md)。

- 日期：2026-10-27。
- 状态：待实施的技术方案，本文件不表示执行能力已接通。
- 范围：DeepSeek Harness 工作台助手中的待办、资讯、知识维护及后台自动化。

## 1. 核心方案

采用「DSH 原生会话与工具调用 + 工作台统一业务服务 + 耗时工作流队列」。

模型负责理解意图、补充上下文和形成工具参数；Host 负责权限、结构校验、目标解析、幂等、并发控制及持久化。模型通过有明确参数契约的工具维护业务对象，避免生成任意脚本或直接编辑状态文件。

既有基础是 `workbenchApi`、27 个 Remote 方法、7 个 Agent 工具和 Client 快照替换机制。先复用这些基础并修复已发现的问题，再补充缺少的能力。

## 2. 两条执行路径

### 短操作

适用：创建、修改和查询待办，修改已存在的资讯，保存知识。

```text
聊天文本 + 项目/选中对象引用
            ↓
DSH 会话中的模型生成工具调用
            ↓
工作台工具 → 统一业务服务 → 校验和持久化
            ↓
返回结构化操作结果 + 新快照/变更版本
            ↓
页面更新；助手显示结果
```

对于明确目标和字段的指令，争取一次模型决策即可调用业务工具。若用户说“把它做完”但未选择对象且无法唯一定位，先查询或澄清目标，不能为减少轮次而猜测。

按钮、看板拖动等已经携带确定操作和对象 ID 的动作直接调用业务服务，无需模型解析。自由文本仍交给模型；不要通过行动词正则把含否定或条件的句子直接当成写操作。

### 长操作

适用：搜索和更新资讯，批量消息识别，较长的研究分析。

```text
聊天指令 → 解析业务参数 → 创建持久化工作流任务
                         ↓
                立即返回 jobId 与当前状态
                         ↓
后台执行：采集 → 筛选 → AI 处理 → 校验 → 写入
                         ↓
        分阶段通知 → 页面更新 → 结果关联回原会话
```

长操作使用独立执行上下文，前台助手提交后可继续接收短指令。Host 工作流队列可在核实版本后适配 DSH 原生 Jobs/Schedule；不能假定原生 Job 接口可以直接执行任意 AI 工作流。

## 3. 请求、工具和结果契约（拟新增）

请求上下文包含：

```json
{
  "requestId": "用户本次提交的稳定标识",
  "projectId": "当前项目ID",
  "sessionId": "关联的原生会话ID",
  "selectedRefs": [{ "kind": "task", "id": "task-example" }],
  "text": "把这条待办标记完成",
  "timezone": "Asia/Shanghai"
}
```

模型只使用工作台允许的业务工具，工具内部统一委托 `workbenchApi` 或新的业务执行服务。建议能力包含任务查询/新增/修改、来源查询/任务识别、资讯刷新/摘要写回、知识保存。

简单操作的工具调用参数示例：

```json
{
  "tool": "workbench_update_task",
  "arguments": {
    "id": "task-example",
    "status": "completed"
  }
}
```

工具名称及业务参数可沿用已有实现；请求关联、幂等和版本检查由 Host 执行上下文或受控包装器附加，不能完全依赖模型自行填写正确。

建议操作结果形态：

```json
{
  "requestId": "request-example",
  "operationId": "operation-example",
  "status": "succeeded",
  "entityIds": ["task-example"],
  "stateRevision": 42,
  "result": { "status": "completed" }
}
```

异步操作返回 `jobId` 和 `queued/running`。任务生命周期建议包含 `queued/running/waiting_input/waiting_approval/succeeded/partial/failed/cancelled`。模型输出文字或提交队列成功都不等于业务修改成功。

## 4. 保证可重试和不丢数据

- 提交层：复用原生 Session 的请求关联与重试机制。
- 业务层：增加持久化操作账本，以 `requestId + operationId` 识别同一操作。一个请求可以包含多个操作；需要保留各自结果与重试状态。来源驱动任务另设稳定来源/事项去重键。
- 存储层：对当前异步状态修改串行化，避免交错读写；写入前完整校验，失败时不留下部分内存修改。
- 冲突处理：增加业务修订号或对象修订号，旧版本修改返回冲突并重新读取。现有 `version` 是 schema 版本，不能用作并发修订号。
- 页面更新：第一阶段保留现有全量快照，附带单调递增的业务修订号；仅接收较新快照。后续根据数据规模再增加增量推送。
- 保留人工确认/修改标记；后台提取不能直接覆盖人工编辑字段。
- 删除、发布、迁移外部系统沿用确认要求；明确授权的普通本地新增/修改通过校验后直接执行。

## 5. 资讯刷新采用固定工作流

“更新最近一天的 AI 资讯”解析成主题、时间范围、数量和项目范围，提交一个资讯工作流任务。

1. 依据已有关注主题生成少量搜索词，复用 DSH 已就绪的联网能力。
2. 对独立查询和页面读取使用有限并发；起始可配置为 2–4，依据宿主和 Provider 限额调整。
3. 单路失败可保留其他已成功结果，任务如实标记 partial；原生批量搜索的失败策略需由适配层核实，不能假定天然逐路降级。
4. 读取原文并核对日期，按 URL 与事件归并，过滤已处理内容。
5. 只对筛选后的重要条目做批量结构化摘要，校验引用与字段后批量写入。
6. 逐步通知“已检索/正在归纳/已保存”；最终统计区分新增、更新、跳过与失败。

同主题和时间窗口正在执行时复用已有 jobId；短期检索缓存与内容哈希减少重复请求。强制刷新可由用户显式提出。持久化缓存策略和操作账本清理策略需在实施时定义。

会话工具调用和后台服务调用都应保持正确的账号、模型路由及权限上下文。前端不接收搜索凭据。

## 6. 提速措施与验证方式

| 提速措施 | 目的 | 验证 |
| --- | --- | --- |
| 选中对象携带稳定 ID | 减少先查列表、再找对象的模型往返 | 明确目标指令的模型轮次与工具次数 |
| 短操作使用有限工具和简短上下文 | 减少无关工具与历史干扰 | 输入量、模型首响应和完整执行耗时 |
| 按需保留当前原生会话 | 减少重复创建与加载 | 冷启动和连续操作分别计时 |
| 长操作入队并独立执行 | 防止资讯刷新阻塞待办操作 | 刷新期间仍可创建和修改待办 |
| 有限并发、缓存、批量摘要与保存 | 缩短资讯链路并控制请求量 | 每阶段耗时、请求数及部分失败结果 |
| 根据业务结果直接同步页面 | 无需等待模型写完总结 | Host 提交到页面可见的间隔 |

记录请求接收、模型开始、工具开始/结束、提交成功、页面可见等时间点，并分别统计模型等待、网络等待和业务处理。现阶段尚无真实延迟实测，不承诺具体秒数。

## 7. 实施顺序与验收

1. 修复原清单 01–03：异步工具、重载 ID/关联、日期和否定语义。
2. 收敛工具到统一业务接口；补充结构化返回、幂等及并发控制。
3. 接入工作台助手到原生会话的短操作，验证选择任务后一次指令完成修改。
4. 接入资讯工作流和任务状态通知，验证长操作期间可继续执行短指令。
5. 增加定时触发、故障恢复与实际延迟测量。

必要验证场景：工具执行及异常、重试不重复、重载关联保持、旧版本写入冲突、资讯部分失败、取消后的提交边界、断线重连、前台短操作不受长任务阻塞。

## 9. 数据持久化与迁移

### 当前实现

业务状态默认位于 `~/.dsh/storages/dev-workbench/state.json`；设置 `DSH_HOME` 后改为该目录下的 `storages/dev-workbench/state.json`。运行时诊断返回的 `dataPath` 是具体宿主的权威路径，不能用当前终端的环境变量替代宿主运行时确认。

同一 Host 数据目录下的项目、任务、来源、执行记录、知识、资讯、候选和设置共用一个 JSON 文档。每次修改先写临时文件再 rename，进程内保存权威缓存；因此运行中从外部替换文件不会可靠刷新内存。

设置页已有「导出 JSON」，导出的是浏览器当时持有的快照，需改为 Host 获取最新一致快照。尚无导入恢复、自动备份和完整迁移包。

### 推荐目标

- 先补齐稳定 ID、关联恢复、损坏保护、备份及导入导出；读取数量上限不能静默截断迁移数据，展示分页与保留策略分别处理。
- 后续本地存储推荐评估 SQLite，将项目、任务、来源、资讯、执行记录、后台任务及操作账本纳入事务与索引。通过统一存储接口接入，页面和工具继续调用业务服务。
- JSON 保留为版本化交换格式，支持检查和跨存储实现迁移；有附件时打包为 ZIP，采用相对路径及安全解包校验。
- 可增加插件自己的可配置数据目录，不依赖源码仓库位置；多个进程访问时使用可靠的写入协调。文件备份与多设备实时同步属于不同能力，多用户场景再评估中心服务与服务端数据库。

### 迁移流程（待实现）

Host 生成一致快照 → 导出版本信息、业务数据和校验清单 → 目标端预检与数量预览 → 检查对象关联和 schema → 映射机器相关项目目录 → 备份目标数据 → 事务导入或暂存校验后切换 → 重载验证 → 失败回退。

工作台的 `sessionId` 只是对 DSH 原生会话的引用，执行摘要不能替代完整会话日志。工作台迁移与 DSH 会话迁移分别处理；目标宿主无法找到原会话时保留业务证据并提示关联不可用。模型、搜索与企业账号凭据不进入普通业务迁移包。

SQLite 如在运行中备份，应使用备份 API 或经过验证的一致快照机制，避免只拷贝活动数据库主文件而遗漏日志状态。依据：[SQLite 应用场景](https://sqlite.org/whentouse.html)、[SQLite 在线备份](https://sqlite.org/backup.html)。

本轮仅核实文件位置和导出逻辑并补充方案，未移动、覆盖、迁移任何真实业务数据。
