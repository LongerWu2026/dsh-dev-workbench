## 1. 交付目标

每天打开工作台，可以看到由别人私聊发来的消息和群内 @本人消息形成的待回复、待处理事项。系统理解具体的会议、开发、登记要求，随着本人回复和后续消息更新状态；技术资讯自动搜索、核对原文并生成摘要；数据可以可靠备份与迁移。

保留现有页面、Host 业务接口和 DSH 会话适配。新增能力优先接入既有模型与工具，不在插件内建立另一套模型凭据、聊天历史或任意脚本执行系统。

## 2. 统一架构

```text
卡片操作 / 助手指令 / 后台触发
              ↓
统一请求上下文（账号、项目、工作区、requestId）
              ↓
确定性采集 → 持久化消息与处理队列 → 原生会话模型分析
                                          ↓
                       结构化结果校验、来源核对和事项合并
                                          ↓
                        统一业务服务：短事务提交 + 操作账本
                                          ↓
                          数据修订号 → 页面与助手结果更新
```

短操作直接执行有契约的业务工具；长操作创建作业后立即返回 jobId。前台可继续处理其他短指令，后台根据阶段状态更新进度。

采集、联网和模型调用不放在串行写入临界区；临界区只执行已经验证的数据变更，避免资讯搜索或 AI 等待阻塞手动待办。

## 3. 数据与契约

### 消息与同步

- 消息身份：账号/组织 + 会话 ID + 消息 ID，均来自 CLI 返回。
- 时间：分别记录原消息发送时间、采集时间、分析时间，并使用明确时区。
- 关系：本人/他人方向、会话类型、@目标、已经验证的回复引用、来源对象。
- 进度：采集游标与分析进度独立。采集成功落库后推进游标；模型失败仅重放处理队列。
- 上下文：以消息锚点和未解决事项为入口，按需读取前后文；以明确引用优先关联话题，避免混用整群历史。

### 事项模型

沿用 Task 及其现有 `status`，兼容新增可选字段：

| 字段组 | 内容 | 约束 |
| --- | --- | --- |
| 义务 | 是否需要回复、是否需要处理 | 两者可同时存在 |
| 回复进展 | 待答复、已确认收到、已实质答复、不需答复等 | “收到”不能自动认定问题已答复 |
| 类型 | 会议、功能开发、登记填报、其他 | 仅知会可留在来源收件箱，不强行建任务 |
| 具体要求 | 标题、交付物、期限、会议起止/地点、登记对象 | 缺失字段留空；询问不等于承诺 |
| 证据 | 来源锚点及多条消息引用 | 保留原有单来源字段的兼容读取 |
| 人工保护 | 人工修改、忽略、稍后提醒、处理确认 | 后台重评估不得直接抹掉人工判断 |

新增字段和集合需有版本化兼容规则，先用旧数据加载/重载测试证明不会破坏既有任务与来源关联。

### 后台作业与提交

- 每个作业记录类型、输入范围、触发方式、阶段、进度、最近错误、尝试次数、下次重试时间及产出 ID。
- 业务操作按稳定的 requestId/operationId 去重；同一条消息拆分的事项具有稳定来源关系，不能每次分析重新建一份。
- 写入采用受控串行化、修订号检查及失败回滚；旧快照不能覆盖更新结果。
- 独立操作可有限并发，同一来源或同一事项的冲突变更需协调；取消与提交边界须明确。
- 仅启用相应配置后运行后台模型流程，说明宿主退出/休眠时的停止及恢复行为。

## 4. 消息处理方案（13–17、19）

1. 使用已有 yzj-cli 适配分页发现会话；读取私聊和群聊增量，保留真实消息 ID 与发送人。
2. 他人普通私聊和群内 @本人作为新事项入口。本人发言及群内相关普通消息参与已有事项的上下文与状态判断。
3. 消息先保存，再推进采集边界；后续 AI 和重试从队列读取，不能因限流或截断跳过未保存消息。
4. 模型按批输出回复/处理义务、具体事项、来源依据、明确事实和待确认字段。
5. Host 校验来源存在、责任指向、时间依据和重复关系。依据明确的本地事项可按配置自动登记；歧义进入待确认。
6. 后续本人答复、代答、取消、已解决或补充要求触发原事项重评估，分别维护回复和实际处理进展。
7. 页面复用现有任务中心，增加待回复/待处理及事项类型筛选，保留来源预览和人工调整入口。

第一阶段登记本地工作台事项；发消息、邀请参会、提交外部表单和执行开发都需要对应的明确指令及权限。群内未 @新事项、主动待跟进和审批聚合保留为后续扩展。

## 5. 资讯处理方案（20）

关注主题/项目和时间范围 → 联网搜索候选 → 读取原文并核对日期 → URL/事件归并 → 筛选重要内容 → 批量生成四段摘要与项目关联 → 校验引用 → 写回对应卡片。

复用现有联网服务、资讯写回工具及 19 的作业框架。RSS 作为可选来源，不要求用户逐个配置网站。区分发布、更新和抓取时间；未知日期不得以抓取时间冒充发布日期。来源不可访问或检索失败保留具体状态，不能显示为“没有资讯”。

先限制候选数量并缓存已处理内容，再进行模型摘要；避免对每个条目进行多轮开放式推理。分别统计新增、更新、跳过和失败。

## 6. 数据迁移方案（21）

先保留现有 JSON 与备份能力，增加一致导出、可检查的迁移格式和受控导入：

1. Host 获取最新一致快照，导出格式/schema/插件版本、数据及校验清单。
2. 目标端预检结构、数量、对象 ID 和交叉引用，预览待导入内容及冲突。
3. 映射机器相关项目路径。明确替换或合并模式，人工字段、旧会话关联和版本冲突有规则。
4. 备份目标数据后，在暂存区验证并原子切换或事务提交；失败保持原数据。
5. 保留稳定 ID 与来源，恢复后递增业务修订号并同步 Client；通过重载证明结果一致。

业务数据、DSH 原生会话历史和账号凭据分别管理，凭据不放入普通迁移包。SQLite 更换在数据契约、并发与查询规模明确后评估，不作为消息闭环的前置条件。

## 7. 界面与反馈方案（22）

- 明确显示采集、分析、校验、写入、完成或部分失败，后台关闭时不显示正在自动处理。
- 统一 RSS 与联网发现文案；明确最近成功时间和当前失败原因，不用全局写入时间代替各业务的新鲜度。
- 后台和助手写入均通过修订号更新页面，编辑期间避免覆盖草稿。
- 失败提供具体对象与可重试入口；结果展示来源、修改字段与已落库对象，模型输出文字不等于操作成功。

## 9. 验证矩阵

| 层 | 必测内容 |
| --- | --- |
| 采集 | 多页会话、单群超页、批次有效来源超上限、失败补采、方向/@对象/通知过滤 |
| 语义 | 待回复/待处理/仅知会、多事项、否定/询问、会议/开发/登记、依据不足 |
| 状态 | 已确认收到与实质答复、交付与取消、代答、后续补充、人工保护、话题不串联 |
| 一致性 | 请求重试、模型重试、并发修改、取消时提交、修订号、重启恢复 |
| 资讯 | 原文来源、日期区分、重复事件、摘要写回、部分失败与无结果区分 |
| 迁移 | 替换/合并预览、路径映射、引用完整、损坏包拒绝、失败回滚、恢复后页面同步 |
| UI | 任务筛选、编辑保护、状态可读、助手与后台结果同步、正确 DSH 页面上的 GUI E2E |

已有构建/语法、Host、渲染与真实 React 测试继续执行，并针对每次实际变更补充有意义的用例。GUI 超时先确认 CDP 目标、工作台根节点定位及条件等待，再跑完整流程；少量真实消息样本的分类效果单独记录，不以 mock 通过代替。
