# 云之家私聊与 @我消息：待回复与具体事项处理方案

> 阶段记录说明：本文件保留云之家 CLI 能力验证与早期方案。CLI 可提供的能力不等于插件已实现的采集范围，当前代码边界以项目说明为准。 [当前项目架构与功能说明](PROJECT-ARCHITECTURE-AND-FEATURES.md)。

- 日期：2026-10-28。
- 结论：以「别人私聊发给我的消息」和「群内 @本人的消息」为默认入口，结合相关上下文识别是否需要回复、是否需要处理具体事项；会议、功能开发、登记填报等登记为工作台事项。
- 验证范围：本机 `yzj-cli 0.1.8` 的命令帮助、安装技能参考、项目当前源码；按用户本次询问只读抽样查询最近会话与一个私聊的少量历史，未调用发送或审批等写操作。
- 项目观察基线：当前代码已有原生助手会话、规则候选、@我 增量采集及后台采集定时器。文档中的“已完成规则部分”不能视为本需求的模型提取和待回复闭环已完成。

## 需求边界（2026-10-28 按用户说明收敛）

- 默认新事项入口包括他人发来的普通私聊，以及群内 @本人的消息。私聊中的本人消息用于上下文和后续状态判断，不要求对方再 @本人。
- 两类消息进入同一识别流程，分别判断沟通与执行义务。问候、感谢、明确只供知悉或已处理的消息保留来源，不自动变成待回复或待办。
- 群内未 @本人消息、本人主动向别人发起请求形成的待跟进、审批聚合均为后续可选扩展；群内未 @消息仍可作为已有事项的相关上下文。
- 本人和他人的关联消息用于判断事项的答复、补充、取消和处理结果。不把本人发言重复建成新待办；自聊、助手和系统通知需单独识别，不混作他人私聊。
- 「登记事件」首先指登记工作台中的业务事项；创建云之家日程、发出会议邀请、提交登记表或执行功能开发属于后续明确指令，不随消息识别自动发生。

## 1. 已核实的 CLI 能力

| 需求 | 已有命令/数据 | 可实现程度与边界 |
| --- | --- | --- |
| 确认当前用户 | `whoami`、`contact user get` | 以 openId 识别本人，姓名用于展示 |
| 发现会话 | `im group recent --page --limit`、`im group search` | 最近会话可分页，支持私聊/群聊等类型识别；不能把第一页当成全部会话 |
| 读取上下文与增量 | `im message list --group-id ... --type newest/old/new --msg-id ...` | 可按消息锚点向前/后补上下文与增量；参考说明每页最多 20 条，要循环排空并验证实际排序 |
| 查找 @与关键词 | `im message search --keyword ... --notify-to-open-id ... --start ... --end ... --page ...` | @人过滤是关键词命中后的附加筛选；关键词仍必填，不能当作无关键词的全量 @我 接口 |
| 判断已读未读 | 会话 `unreadCount`；`im message read-status` | 会话未读数仅供优先级参考；消息回执只能查自己发的，群聊需适用的 @提醒且有时效；不能直接判定“别人发给我的哪些消息尚未回复” |
| 获取结构化审批事项 | `approval flow list --type todo/unread/done/read/myflow/follow`、`approval flow get` | 审批待办/待阅可确定性同步，权限限当前登录用户可见范围 |
| 读取文档和日程 | `doc get`、`doc download`、`calendar event list/get` | 适合作为指定事项的证据；文档搜索主要是标题和文件名，不能宣称全企业正文检索 |
| 生成并发送回复 | 模型生成草稿；`im message send --reply-msg-id ...` | 技术上可引用原消息回复；本次不执行发送，未来发送遵守技能的目标与最终文本确认要求 |
| 写入云之家原生任务 | 当前根命令无独立通用 `todo` 域 | 工作台本地建任务可实现；不能把审批列表或本地 Task 宣称为云之家全部原生任务。可选使用多维表格承载共享事项 |

依据：本机命令帮助及 yzj-cli 技能的 `references/products/im.md`、`im/message.md`、`im/group.md`、`approval.md`、`contact.md`。私聊列表和少量消息读取已抽样验证；其他接口权限、完整分页覆盖及引用字段仍需分别验证。

### 本次只读抽样结果

`im group recent --limit 20 --page 1` 成功返回 20 个会话，其中 `groupType=1` 的私聊 4 个，且 `more=true`。选择一个最近由对方发言的私聊，使用接口返回的 groupId 读取 `im message list --type newest --limit 5`：成功返回 5 条，3 条来自对方、2 条来自本人，每条均含消息 ID 和内容字段。

因此当前账号与 CLI 确实可以读取普通私聊及双方对话，识别入口可以包含无需 @的私聊入站消息。本次仅验证最近一页和一段对话，不宣称所有历史均已扫描；未将原始 ID、正文或凭据输出到报告。

## 2. 识别结果与具体事项类型

| 类型 | 判断依据 | 示例 |
| --- | --- | --- |
| 待回复 | @本人提出问题或要求确认，尚无有效答复 | “@你 这个版本能否今晚发布？” |
| 会议事项 | @本人要求参加、安排或准备会议 | “@你 明天15点参加需求评审” |
| 功能开发事项 | @本人明确要求开发、修复或交付功能 | “@你 周五前完成导出功能” |
| 登记填报事项 | @本人明确要求登记、提交材料或填报 | “@你 今天18点前完成工时登记” |
| 其他处理事项 | @本人明确交办的其他工作 | “@你 整理本次压测报告” |
| 仅知会 | 无个人答复或执行要求 | “@你 供了解，已经处理完毕” |

识别结果至少包含两个独立维度：`needsReply`（沟通义务）与 `needsAction`（执行义务），执行义务再记录 `eventType`，建议为 meeting/development/registration/other。同一条私聊或 @消息可同时要求回复和处理，采用同一套事项提取规则。

例如“@你 周五完成导出功能，并回复一下排期”，形成一个功能开发事项并附回复要求。回复“收到”记录为已应答；排期是否已说明、开发是否已交付仍分别根据证据判断。一条消息含多项独立工作时拆成多个关联事项，保留同一原始消息引用。

“周五能完成吗”只构成期限可行性的询问，不能自动当成本人已承诺周五交付。会议只给开始时间时保留结束时间为空，不能默认补齐时长；登记事项要明确登记对象和产出要求。

未读、无人后续发言、本人之后说过话，都不能单独作为是否待回复的充分条件。没有观察到回复，须区分确实未回复、采集缺口、其他渠道已处理和需要人工确认。

## 3. 项目当前具体缺口

1. `src/host/37-yunzhijia.js:327` 仅取最近会话第一页，并只扫描前 10 个群，每群单次取 20 条；尚未完成覆盖范围内会话和消息的排空翻页。
2. `:358–359` 只保留判定为 @我的消息，并排除本人消息。需要增加私聊分类，保留他人私聊入站消息；同时补充两类消息的前后文与本人后续回复，识别待回复及是否解决。
3. `:440–448` 先更新所扫描群的游标，再把待入库 @消息截到 20 条；当命中超过上限时存在遗漏风险。应先可靠保存全部采集消息或待处理队列，再推进到已保存边界。
4. `src/host/38-candidates.js` 当前是行动词、日期、指向性等规则打分；可做候选预筛，没有模型级对话判断，也没有待回复状态机。
5. `src/host/45-automation.js` 当前定时器执行资讯与 @我 采集；未自动串起消息上下文补齐、模型提取、事项合并与回复状态重评估。
6. 现有 Task 尚未表达回复义务、执行义务和会议/开发/登记等事项类型，且单个 `sourceRefId` 不足以表达一段对话的多条依据。

这些是针对新增需求的代码分析结果，并不表示本轮已修复。

## 4. 推荐架构

```text
本人身份 + 授权可见范围
        ↓
yzj-cli 分页增量读取 → 他人私聊入站 / 群内 @本人
        ↓
以入站消息为锚点补齐相关上下文、本人后续答复和处理结果
        ↓
确定性预筛 + 对同一事项的关联消息归并
        ↓
DSH 模型识别：需回复？需处理？具体事项是什么？
        ↓
Host 校验依据、关联与去重
        ↓
同一任务中心：待回复 / 待处理 → 会议、功能开发、登记等
        ↓
新消息触发重评估 → 更新已有事项 → 必要时提醒
```

现有工作台助手会话可用于人工触发分析；自动化需要增加有幂等与进度记录的模型任务执行器。审批聚合另列可选扩展，采用结构化接口，不影响本期 @消息识别闭环。

## 5. 采集与状态设计

- 新事项来自他人普通私聊和群内 @本人，按授权范围分页发现并支持会话范围配置。`groupType=1` 识别私聊，再以本人 openId 区分发送方向并排除自聊；`groupType=2` 的群聊识别 @目标。@他人、助手/系统通知不默认生成新事项；@全员单独标记并核对是否有明确个人义务。
- 初次运行回溯可配置窗口，之后按群游标增量。定期补扫所选会话，并保留未解决事项的低频重查，即使会话不在最近第一页也不能失去跟进。
- 先保存消息和处理队列，再推进采集游标；另设分析进度，AI 失败可重跑已采集数据，不重新抓取或丢弃消息。
- 去重键包含账号/组织、会话、消息 ID。事项级合并按来源锚点和话题关系进行，同一事项的补充消息追加证据并更新，不反复新建。
- 单独记录消息发送时间、采集时间和分析时间。期限以消息发送时间与明确时区解释。
- 接收消息若返回明确引用 ID，优先建立回复关系；返回字段未验证时不能猜字段名。缺少明确关联时使用受限上下文的语义判断，并标明不确定。
- 建议在已有任务模型补充回复义务、执行义务、具体事项类型、回复/处理状态和多来源引用，保持现有任务状态契约。会议补开始/结束/地点等可空字段，其他事项保留期限、交付物及依赖。任务中心沿用现有列表，提供待回复/待处理和事项类型筛选。
- 模型返回结构化结果及支持它的 msgId、明确事实和待确认字段。每条写入验证来源存在、本人责任、时间依据及重复状态；人工修改字段受保护。
- 处理已回复、取消、转交、其他人代答等后续消息；人工“已处理/不需回复/稍后提醒”应保存稳定判断，防止下一次同步重新弹出。

## 6. 两种接入方式

### 第一版：yzj-cli 增量轮询 + DSH 模型

最适合在现有项目上推进。使用已有个人授权和只读命令，不引入新的企业消息接入链路。可从 2–5 分钟同步间隔开始评估；具体取决于会话数、接口限制和模型耗时，不能承诺秒级实时。

本机 CLI 当前没有持续消息订阅命令。DSH 进程退出时，现有插件定时器停止；持续运行需要实际的常驻宿主或后续部署。

### 扩展：机器人事件入口 + CLI 补齐

云之家官方介绍了机器人 WebSocket 接入，金蝶维护的 `kingdee/openclaw-yzj` 也提供了相关实现。可将收到的机器人事件作为实时触发，由 CLI 查询已授权上下文和补漏。

机器人可见范围与个人账号历史可见范围不能等同；目前未验证机器人是否覆盖目标私聊或群，因此它是补充入口，不能直接替代个人事项扫描。接入不意味着必须更换现有 DSH 工作台，也不在本轮创建机器人或配置网络通道。

参考：[云之家机器人官方介绍](https://open.yunzhijia.com/home/dynamic/news?article_id=69c63cdeac46a95293373ffb&source=dynamics)、[kingdee/openclaw-yzj](https://github.com/kingdee/openclaw-yzj)。

另有社区项目 [GuoxinShan/dsh-yzj](https://github.com/GuoxinShan/dsh-yzj) 提供 CLI 桥接和事项管理思路，可作为设计参考；本次未安装，也未验证其与当前宿主的兼容性或处理效果。

## 7. 第一阶段范围与验证

第一阶段实现：完整采集他人私聊入站和群内 @本人消息、回复/处理义务识别、会议/功能开发/登记等事项提取与落库、后续回复和处理状态重评估。审批聚合、群内未 @新事项扫描和主动待跟进保留为后续可选范围。AI 回复草稿也可后续增加，发送与事项识别分开处理。

实施验收至少覆盖：

- 一轮新增消息超过 20 条、最近会话超过 10 个时不漏采，分页失败不错误推进游标。
- 普通私聊无需 @也能触发同一识别流程；本人发言、自聊、群内 @他人、@全员、机器人和系统通知能够区分；仅符合默认范围且有明确义务的消息产生新事项。
- 后续本人答复、其他人代答、取消、已有处理结果和跨话题聊天不误判。
- “收到”和“已交付”分别更新回复与交付状态。
- 同一消息同时要求答复与交付时两个维度均保留；会议、开发、登记类型及多事项拆分正确；仅知会不误建义务。
- 会议未给结束时间时不补时长；“能否周五完成”不误认承诺期限；登记事件不触发发消息、日程邀请或外部表单提交。
- 重复同步、模型重试、重启和人工忽略不产生重复事项或重复提醒。
- 在用户允许的少量真实会话窗口做人工标注，分别检查采集覆盖、抽取准确性和回复状态判断。接口读取是否影响未读状态、消息排序、引用字段及账号权限需实测。

本报告不包含任何真实会话 ID、消息正文或账号凭据。
