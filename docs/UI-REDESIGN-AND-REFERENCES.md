## 1 改版前的问题与代码证据（8c32b56基线）

| 问题 | 改版前静态证据 | 改版要求 |
| --- | --- | --- |

| 错误详情占据首页 | 首页同步条直接呈现采集报告的 `note/status` | 首屏显示简短原因、影响范围、重试；技术错误和原始明细折叠 |
| 页面与助手争宽 | `WorkbenchApp` 并列渲染正文与 `AssistantDrawer` | 根据插件实际可用宽度决定停靠或专注视图 |

## 2 可重复的社区方案检索方法

1. 用 DSH、DeepSeek Harness、workbench、sidebar、task-board 等关键词检索 GitHub；生态列表和搜索榜单只用于发现候选。
2. 打开仓库，确认作者、是否为 fork、上游、默认分支、README、许可证与维护记录；同名项目不视为同一个产品。
3. 使用 GitHub 仓库 API 记录 `stargazers_count/forks_count/pushed_at/license/fork/parent`，标明采集日期；再读取默认分支的 README、`package.json` 和相关源码。
4. 分别核对宿主版本要求、插件版本、Node 运行时、Client 注入依赖；插件版本号不能当作 DSH 版本号。
5. 对照官方 UI 插槽、安全区与主题契约，区分「可借鉴的交互」和「可直接复用的实现」。
6. 如后续选型需要运行，先在独立 DSH profile/测试数据中评估加载、权限、依赖冲突和卸载恢复；本轮不直接安装到现有环境。

可重复的只读查询：`GET https://api.github.com/repos/{owner}/{repo}`。`pushed_at` 仅表示仓库最近推送，不证明最后发布版本可用或全部功能稳定。

## 3 目标信息架构

目标顶部目录：**今日｜待办｜待回复｜资讯｜知识｜更多**。顶部操作区保留快捷新建、助手入口；统一搜索和连接设置放入「更多」，搜索继续复用快捷键，避免重复入口争占首屏。

| 目标目录 | 用户需要完成的事 | 当前落点与实施边界 |
| --- | --- | --- |
| 今日 | 看最紧急待办、待回复和少量重点资讯 | 重构现有 `dashboard`，不是再加一套独立统计首页 |
| 待办 | 筛选、编辑、完成实际处理事项 | 复用 `tasks`；会议、登记、开发等是任务类型或筛选 |
| 待回复 | 查看需要答复的消息、依据与关联任务 | 0.2.0 已实现 `Reply` 独立页、来源依据、关联任务及识别队列；桌面模型代表样本通过 |
| 资讯 | 查新资讯、看摘要与原文、收藏或转为任务 | 0.2.0 已实现完整独立页、后台摘要和作业结果；真实联网与模型闭环通过 |
| 知识 | 收藏与维护可复用内容 | 复用 `knowledge` |
| 更多 | 搜索、Agent 中心、开发工具、研发协作、连接设置 | 保留现有能力与路由，逐步调整展示位置 |

最初的分步方案先将原有八页改为横向导航，再增加待回复和资讯页；0.2.0 已一并实施，保留 `WB.ORDER/WB.go` 路由和快捷键兼容，「更多」收纳次要模块。

0.2.0已增加Reply与资讯完整页并启用目标顶部目录，原有八页均保留；实际实现范围和验收状态以实施记录为准。

页面内容只在一处维护。今日页显示摘要与「查看全部」，完整处理到对应模块；待办与待回复独立计数、独立完成，不能把「已回复」等同于「事项已处理」。

## 4 首页与操作流程

- 顶部状态行：显示最近同步时间和紧凑计数；异常时显示「部分会话未同步」及重试入口，展开后查看采集、分析、写入各阶段。
- 主要区域：优先显示待办与待回复清单。每行给出标题、来源/联系人、时间、状态及一个主要操作，来源证据可展开。
- 次要区域：资讯显示少量标题、来源、发布时间与摘要入口；更多内容进入资讯页，不用长资讯列表撑高空任务卡。
- 空态：说明当前为何没有内容，并给出一个有效动作，例如新建、同步或调整筛选；高度随内容，不保留巨大插画占位。
- AI 状态：待识别、待确认、失败、完成具有一致文案；「开启 AI」「运行分析」「查看结果」分别对应真实前置条件。
- 操作反馈：区分成功、部分失败、等待确认；禁止把已入队显示成已完成。失败可定位来源、重试和保留草稿。

从消息进入处理的目标路径是：来源消息 → 查看识别依据 → 建立或关联 Reply/Task → 编辑必要字段 → 跟踪结果。AI 先整理信息、调用同一业务用例；界面保持人工修正入口。

## 5 助手、详情与宿主布局边界

助手是工作台内可打开的上下文操作入口，现有 `AssistantDrawer` 和原生会话接入可复用。点击消息、任务、资讯时，将明确选中的对象作为引用交给助手，不默认把整份数据塞入上下文。

0.2.0同一时刻只显示助手或任务编辑侧区，切换时保留任务草稿。回复原消息在行内展开；资讯和知识编辑沿用聚焦弹窗，避免再常驻一列。更完整的详情统一仍以实机操作反馈评估，不把原型中的所有细节视为已验收。

宽容器可在正文右侧停靠，宽度建议 320–400px；这是插件内部设计尺寸，并非宿主 API 保证。当前自绘助手与全局 `main` 页面是否能直接复用官方右栏，须在实际宿主版本做能力探测。

仅检测到 `ui-sidebar-right` 服务，不足以证明当前工作台主页面拥有可见的右栏座位。需要验证全局页、会话页、页面切换和销毁行为；不可用时采用插件内部同一侧区，避免依赖宿主私有 DOM。

窄容器打开助手或详情后，用单页专注视图替换列表；提供清晰返回按钮，返回后恢复滚动、筛选与焦点。此时不常驻第三列，也不以过窄正文和过窄聊天区勉强并排。

### 窗口安全区

以官方 [ui-layout 的 Window Chrome Seat](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-layout/README.md#window-chrome-seat) 为准：`--dsh-frame-leading-clearance` 用于顶角窗口控件避让，`--dsh-frame-top-clearance` 用于主页面顶部安全区。

macOS 主页面顶部安全区按宿主契约可为 48px；浏览器端使用 `var(--dsh-frame-top-clearance, 0px)` 等回退。先确认宿主容器是否已经留白，由一层负责补偿，避免出现双重顶部空白。

顶部目录、按钮和可交互区域必须避开窗口控制按钮及拖拽区域；宿主侧栏展开、折叠、全屏与浏览器访问都要验证，不把截图中的固定像素坐标写成布局规则。

## 6 按容器宽度响应

断点依据 `.wb-root` 实际可用宽度，优先使用 CSS container queries；必要时用 `ResizeObserver` 提供模式状态。不要只看窗口宽度，因为宿主侧栏、右栏与缩放都会改变插件空间。

| 插件容器宽度（建议值） | 顶部与正文 | 助手 / 详情 |
| --- | --- | --- |
| ≥1200px | 顶部主要目录完整；首页可采用主清单加较窄资讯区 | 可停靠单侧区；正文不足时自动改专注视图 |
| 900–1199px | 目录按空间进入「更多」；正文优先单列，适量并列摘要 | 仅当正文仍有约 560px 可用宽度时停靠 |
| 600–899px | 紧凑顶栏；目录横向可滚动或更多菜单；列表单列 | 单页专注视图，返回恢复列表状态 |
| <600px | 操作收纳；导航保留当前项与目录入口；文本允许换行 | 全宽专注视图，输入与主要按钮保持可操作 |

这些是设计起点，需用真实中文内容、宿主缩放和最长错误信息校正；不把宽度范围当作业务功能可用性的限制。

页面遵循一个主要纵向滚动容器；只有目录或必要代码内容可横向滚动。标签与按钮不得仅靠图标表达，当前项、键盘焦点及未读/待处理数量在明暗主题下均清楚可见。
