# 知识空间与办公助手改造建议

日期：2026-10-28。状态：本文件保留整改前盘点与总体建议；本地自动检索及办公接入已实施，最新范围与证据见[实施记录](KNOWLEDGE-RETRIEVAL-IMPLEMENTATION-2026-10-28.md)。未部署外部知识服务。

## 整改前缺口与证据

当前有知识增删改查、收藏/笔记/片段、字面搜索、手动添加聊天上下文和Agent工具查询。它们提供了使用知识的入口，但未形成默认可靠的检索问答链路。

- `src/host/assistant/sessions.ts`：`sendAssistantPrompt` 和 `runAssistantAsk` 使用 `buildAssistantContext(..., input.refs)`，依赖用户指定引用，没有统一的回答前知识检索。
- `src/shared/assistant-context.ts`：Host按ID读取最新知识正文，已有引用容量边界，可以复用。
- `src/host/search/unified-search.ts`：知识使用字符串包含匹配，截取前一批结果，缺少问题改写、分块召回和相关性排序；该知识分支未过滤归档条目。
- `src/host/api/tools.ts`：`workbench_search` 已要求模型取证，但回传每组最多6条、每条摘要最多80字符，未附可直接读取片段正文的统一引用契约。
- `src/host/api/office-tools.ts`：知识list可返回正文，但依赖模型选择工具，查询方式仍为字面匹配。
- `src/host/workflows/office-jobs.ts`：回复、报告、待办方案读取各自事项快照，尚未读取知识库。后台模型禁止调用工具，因此不能只增加一个搜索工具来补齐。
- 知识条目以标题、正文、URL和标签为主，缺少项目/账号范围、版本、来源定位、索引状态和审核状态。

因此，“模型完全无法读取知识”并不准确；准确的问题是没有默认召回、稳定引用和工作流共用能力。

## 建议定位

把工作台组织为“资料 → 可检索知识 → 当前事项 → 交付产物 → 经确认的经验”。知识库为聊天和办事提供依据，任务记录当前执行状态，两者关联而不混写。

建议形成三类内容：原始资料（消息、文档、原文）、已确认知识（规范、方案、FAQ、排障结论）、个人偏好/项目约定。模型回答和资讯摘要先作为候选，用户确认后才成为长期可信知识；未审核内容可按显式模式检索，并显示状态。过期规范保留历史但默认不参与当前建议。

## 统一技术链路

```mermaid
flowchart LR
 A[聊天问题或办公作业] --> B[确定项目/账号/知识范围]
 B --> C[检索相关片段并排序]
 C --> D[去重、版本检查、上下文预算]
 D --> E[Harness已有模型生成]
 E --> F[校验引用并展示来源]
 F --> G[人工采纳或执行验收]
 G --> H[候选经验审核入库]
```

先通过现有TypeScript Host实现 `KnowledgeService.retrieve(query, scope, options)` 与 `readChunks(ids, scope)`，供三种入口共用：

1. 侧边助手和同步问答：默认自动检索；明确通用闲聊可跳过。提供自动/仅知识库/关闭三种模式。
2. 原生Agent工具：增加可返回片段ID、知识版本、定位和正文的检索/读取工具；保留现有统一搜索用于发现。
3. 后台回复、待办方案和会议流程：在模型调用之前由Host注入知识证据，不能依赖被guard禁止的模型工具调用。日报的完成/进度事实仍取自当期任务和执行回执，知识只提供规范或模板。

初期每轮候选约20个，选取约3–6个片段、设置总上下文预算，均为待评测的初始参数；超长内容按标题/段落切分，代码块保留结构。相邻命中合并并返回必要上层段落。中文需分词/字符组合与英文标识符适配，不能沿用整句includes。

先实现本地全文检索与分块、排序、引用，形成可用基线；随后按离线问题集评估是否增加向量与重排。向量模型是独立能力：已有聊天模型配置不代表提供Embedding接口。缺失时继续使用本地检索，不阻断问答；不擅自新建收费服务。

提供 `KnowledgeRetriever` 适配层，后续可以选择Local或外部RAGFlow等提供者。外部检索只返回证据，最终回答仍使用Harness模型，避免重复维护聊天历史。外部接口须在配置时检测版本和能力；本轮未接入或发送企业资料。

## 数据与生命周期

建议对象：

- `KnowledgeDocument`：现有ID、项目/账号范围、来源、版本、内容哈希、审核/有效状态。
- `KnowledgeChunk`：文档ID和版本、段落/页码/行号、正文、索引版本。
- `RetrievalTrace`：请求/作业ID、查询范围、候选/选中片段、耗时、状态。
- `AnswerCitation`：回答位置与实际送入模型的片段ID、文档版本及原文定位。

先保留现有知识ID与state.json记录，索引作为可重建派生数据；使用单独的索引仓储接口。数据量或性能证据需要时再选SQLite/向量存储，不立即迁移整个工作台。迁移包保留原文、来源及版本，索引可重建；缓存键包含正文哈希、索引/模型版本及访问范围。

权限和项目筛选在检索、读取及上下文组装阶段均执行。更新后重建对应片段；归档、失效、删除后立即禁止作为新回答依据。不能只在页面隐藏记录。原文抓取失败与正文为空要显示不可用，不能把URL或摘要当成全文。

没有命中时说明未查到；检索异常与未命中分开。仅知识库模式不得悄悄转成联网/模型常识回答。正常模式的外部或常识补充单独标注。引用ID存在只证明来源存在，仍需用抽样评测和人工反馈检查回答是否被原文支持。

## 界面与实用场景

继续使用顶部目录和已有侧边助手，不再叠加永久侧栏。知识页提供知识集/项目筛选、来源与版本、审核/索引状态，以及“检索测试”入口。回答下方显示来源卡片，点击后在现有详情区域定位原文；可查看本轮检索范围和无命中原因。

| 日常问题 | 应使用的资料 | 有用产物 |
| --- | --- | --- |
| 之前分区数据量过大是怎么处理的 | 同项目排障结论、相关任务和交付记录 | 既有处理办法、适用条件和原始出处 |
| 帮我回复这个接口什么时候支持 | 当前任务进度、接口文档、对外承诺记录 | 有依据的草稿；缺少时间依据就保留待核实 |
| 实现这个新功能需遵守什么规范 | 项目约定、接口/权限规范、历史实现结论 | 开发步骤和验收清单，标出沿用规范 |
| 准备本周项目汇报 | 当期任务/执行证据，历史报告模板 | 真实进展和阻塞，知识只提供格式及背景 |

## 实施顺序与验收

1. **P1：自动检索与引用**。接通聊天两条提交路径、分块/排序、原文读取、引用、无命中/异常；先用已有笔记和片段验收。
2. **P1：知识生命周期与范围**。项目/账号、候选/确认/失效、更新重建、归档移除；补齐当前归档知识仍可被搜索命中的问题。
3. **P1：知识驱动办公流程**。批量回复、待办方案接入同一检索服务；冻结每次作业实际使用的知识版本和片段，不覆盖人工草稿。
4. **P2：扩展召回与采集**。实测后增加可选Embedding/混合检索/重排、复杂文档提供者及增量同步。
5. **P1贯穿：质量可观测**。建立中文问题、同义表达、接口标识符、跨项目、过期版本、无答案和恶意原文等样本；记录召回、引用、答非所据、延迟和Token预算。

建议首批至少30个真实脱敏问题，人工标注相关片段与不可回答样本。验收包括：不手动添加引用能命中；换一种问法仍可找到关键资料；点击引用能定位；编辑/归档后不再用旧版；其他项目不能混入；资料不足明确说明；工作流确实用了知识且草稿人工保护仍有效。没有这些证据，不能把新增向量库视为知识库改造完成。
