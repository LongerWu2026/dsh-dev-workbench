# 新私聊未读漏入任务的修复

用户报告的“代码记得提交”已在原版 DeepSeek Harness 任务中心显示为“提交代码”，状态为待处理，描述保留原消息。实际消息于北京时间 2026-10-29 17:18:41 收到；工作台于17:28采集，于17:29完成识别。本轮没有向同事发送消息或修改云之家未读状态。

## 原因

只读 CLI 查询确认该私聊未读数为2，正文接口也返回原消息；修复前工作台没有对应来源、识别记录或业务记录，因此不是 AI 将它识别为无须处理。

旧群消息历史补采优先于新私聊，占用了每轮正文请求额度，随后云之家限流。另一个问题是未实际采集、仅报告冷却的刷新也会更新报告时间，而调度器将该报告时间当作同步时间，跳过当前五分钟时槽。即使最新消息被采集，同会话历史补采未结束也会挡住识别。

## 修改

- 采集顺序优先新私聊未读，再处理群@与其他补采。
- 最近会话接口已返回的私聊最新入站正文，在账号、消息ID、时间、未读和安装日期范围都可核对时直接入库；正文接口随后限流也保留它。会话页与正文页按会话ID/消息ID去重。
- 当前收件箱可验证的最新私聊未读可以先进入识别；其他历史消息的补采依赖继续保留。旧消息仍继续分页，未宣称整段历史已补齐。
- 五分钟时槽依据实际尝试时间和收件箱快照时间去重，冷却提示本身不消耗时槽。原09:00–21:00工作时段不变。
- 分流规则不变：私聊未读先进入待回复；AI确认是具体事项后只保留待办，原待回复记录标记为已转待办，避免两个活动入口重复。

## 验证

- `pnpm check`：类型、166模块架构边界、构建一致性与语法检查通过。
- `pnpm test`：全量通过，包括26个重点采集场景、36个批量识别场景、13个消息调度场景和217项React测试。
- `pnpm test:layout`：143个场景通过。
- 原版软件重新加载组件后执行只读同步，实际消息采集成功、识别完成，创建“提交代码”；待回复历史为“不需回复 / task”。
- 原版任务中心实际可访问性树显示“提交代码”“代码记得提交”和“状态 提交代码：待处理”。未用手动插入业务状态替代采集验证。

限制：云之家限流仍可能推迟后续消息/历史补采，本次修复不保证任意限流情况下所有会话即时排空；多日运行、真实第二账号及本人实际答复的完整序列仍保留原待办。脱敏证据见[验收记录](evidence/private-unread-intake-fix-2026-10-29.json)。
