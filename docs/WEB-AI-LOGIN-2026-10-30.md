# 多 AI 官网登录保留与状态识别

最新状态：已按用户确认更新 `/Applications/DeepSeek Harness.app` 日常入口，并通过从原应用标识完整重开的 Kimi 登录恢复验收。原版已完整备份。见[日常入口修复记录](WEB-AI-DAILY-ENTRY-2026-10-30.md)。以下保留最初独立副本阶段的实施与验证经过。

本次实现 rc.5 宿主持久化分区及工作台的独立登录状态提示。后续已按用户确认切换到独立原生副本，Kimi 真实登录在完整退出、冷启动后直接恢复。原安装包没有替换，个人 Cookie 和模型配置没有迁移，副本沿用现有业务 home、独立保存浏览器缓存。部署基线、构建、哈希校验和宿主测试见 [rc.5 集成说明](../host-integration/rc5/README.md)。

官网按厂商及宿主 profile 分区，跨主题复用同一厂商登录。持久 Cookie（含 HttpOnly）、localStorage、IndexedDB 保留由 Electron 管理，扩展不导出认证材料。普通 session Cookie 会在完整干净退出后失效，不延长服务器有效期或恢复注销的认证。

工作台在 DOM 就绪、官网内导航和可见时每 5 秒执行只读探测，也提供「重新检查登录」。六站分别限定官网域名及登录路由，以可见登录表单、安全验证控件、可靠个人菜单语义返回「已识别登录 / 需要登录 / 需要验证 / 登录待确认」。输入框、logo、聊天正文里的登录文字不足以判定账号有效；缺少可靠 DOM 证据保持未知。Kimi 额外检查头像与可见账号文字匹配、临近升级入口、主导航及官方域名内的历史入口，兼容 bare/www 域名和隐藏的“查看全部”入口。仅返回固定状态或四项结构布尔标记，不返回账号文字。其他五站及第三方 OAuth 尚未真实账号验收。

填写、发送和上传前重检，遇到明确登录/验证要求暂停操作。导航会清除旧状态，旧文档和已卸载页面的迟到结果不会回填状态或触发填写。工作台仅接收固定状态文字，不接收网页身份资料；状态保留在当前 UI 内存，不进入业务问答、RPC 或导出。
