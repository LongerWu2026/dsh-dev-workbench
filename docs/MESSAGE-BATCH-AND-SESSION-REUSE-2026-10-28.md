# 消息批量识别与后台会话复用

2026-10-28；工作树变更，未提交或发布。

## 当前行为

同一个云之家账号使用一个持久化后台识别会话，不再按六轮主动新建。人工聊天和资讯摘要各自保留独立用途。业务上的“同一个问题”通过原聊天、项目、Task / Reply ID 关联，避免按消息建立新会话或重复待办。

| 时钟 | 当前配置及含义 |
| --- | --- |
| 完整采集 | 本机保留每60分钟拉取新消息、资讯；设置可选5/15/30/60/180/720分钟 |
| 后台检查 | 每60秒检查到期、分页续采、模型积压及持久作业；上一轮仍在执行时单飞等待 |
| 页面刷新 | 每12秒读取工作台本地状态；不因此调用模型，也不表示已拉取云之家新消息 |
| 每批消息 | 本机保留5条，可选5/10/20；消息不足也可以提交，不必凑满 |

退出或休眠期间不执行；恢复后续处理。上述是调度间隔，不能当作端到端完成时限；网络限流、续采和模型运行会延后结果。

## 提交与校验

1. 同账号消息合批，一次模型请求处理多个来源；不同账号分批。以原消息时间排序，原聊天和项目作为关联范围。
2. 首批发送固定识别规则、消息、必要上下文和最新事项快照。后续批次发送JSON增量：新消息、变化的上下文、当前Task / Reply快照。已发送上下文用SHA-256指纹缓存，编辑后重发，最多保留256条指纹。
3. 每批携带batchId，每条返回sourceId；Host逐条检查结果与来源。结果乱序仍能正确写回；漏项、非法字段只将对应消息保留为失败。未知/重复sourceId或错误batchId拒绝整份响应，最多在原会话修复一次。
4. 同批后续消息可以通过临时引用关联前序新建事项，由Host转换为真实ID。不能引用未提交、取消或其他聊天/项目的对象。本人“收到”不等于实质答复或业务完成；人工编辑保护仍生效。
5. 模型等待不占写入队列。提交前重读权威状态；消息被编辑则原结果不写回，释放租约重新排队。单条坏结果不阻断其他有效条目。
6. 大批次超过40,000字符时拆分，不截断原消息；最多20条。单条消息仍受既有来源长度约束。
7. 同一后台会话忙时保留排队，不建立替代会话。首次启动、持久会话真实丢失才创建；冷启动利用公开sessionController.state的cursor继续原ID。丢失恢复重发完整规则。
8. 会话压缩后重新发送协议及所需上下文。模型服务故障仍有限退避，业务失败仍按原有上限重试。会话和指纹保存在本机状态，不进入业务迁移包。

后台工具guard和工作台人工助手选择器识别当前及历史后台会话。宿主左侧已经产生的旧会话日志保留，未删除、未批量归档。后续不会因固定轮数继续堆积；真正丢失会话或增加账号仍可能需要新的后台会话。

## token 的实际边界

不重复提交规则，确实减少了新增请求内容及模型请求次数；复用会话仍会携带历史模型上下文，不能声称历史免费或总token必然持续下降。本机实测原生usage中既有缓存命中，也有缓存较少的轮次。费用依赖模型提供方、缓存和宿主压缩。

宿主提供[自动上下文压缩](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/README.md)，插件不再用“每六轮新建”代替它。调用依照公开[Session Controller类型](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/api/session-controller/src/types.ts)。
