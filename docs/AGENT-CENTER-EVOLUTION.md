# Agent 中心现状与办公执行方案

日期：2026-10-28。本文件保留升级前盘点与整体设计；三类办公流程已进入实现，最新范围与验收见 [办公执行实现记录](AGENT-WORKFLOWS-IMPLEMENTATION-2026-10-28.md)。其余建议不能视为已交付。

## 升级前实现

当前 Agent 中心主要是执行记录台账，而非通用任务执行器。

- Client `features/agents/agent-center.ts` 读取 Host 的 `data.runs`，展示状态、关联任务、步骤、证据、会话ID和耗时；支持筛选、登记、编辑和标记完成/失败。
- Host `application/task-service.ts` 与 `domain/task-commands.ts` 持久化执行记录。`workbench_record_run` 工具允许模型登记结果，有幂等键并可补入当前会话ID。
- `profile` 当前只是记录中的角色标签，不会据此装配不同工具权限或自动启动不同 Agent。
- “执行队列”显示的是 runs；真正可排空、重试的后台 `jobs` 目前只有消息识别 `analysis` 和资讯摘要 `summary` 两类。两套对象尚未形成通用执行闭环。
- “待审批”来自执行记录的 `waiting_approval` 状态，不是宿主待批准命令的实时查询。页面内完成/失败只修改记录，不能批准命令，也不能据此证明命令已执行。
- 执行记录完成不会自动把关联 Task 标为完成，这是应保留的业务边界：还需要交付证据或用户判断。

工作台其他模块已具备消息识别、任务/回复关联、单条回复草稿生成与保存、提醒、ICS导出、模型会话复用、质量评估和预算等基础能力。下一步应组合已有能力，避免重新做一套聊天或草稿系统。

## 最有价值的工作流

| 优先级 | 入口与场景 | 可交付结果 | 需补齐的能力 |
| --- | --- | --- | --- |
| P1 | 待回复：批量准备回复 | 按事项组织的草稿、依据和待补信息 | 从单条草稿扩展为可恢复批次；串联原消息上下文及相关任务状态；保护人工修改 |
| P1 | 待办：帮我处理这件事 | 资料汇总、处理步骤、文档/检查报告/回复草稿 | 从任务启动工作流，限定项目和工具，产物回写、失败重试、结果验收 |
| P1 | 今日/本周工作整理 | 已交付、进行中、阻塞、下步计划及来源 | 将任务、消息与执行证据按项目汇总；避免把“计划做”写成“已完成” |
| P2 | 会议前后 | 会前议题与背景、会后决议和任务 | 复用事件字段、提醒和ICS；纪要来自用户提供的材料，不假设能获得录音 |
| P2 | 开发问题诊断 | 日志摘要、关联代码位置、复现与测试报告 | 明确项目目录和命令范围；分开诊断、修改、发布三个阶段 |
| P2 | AI资讯/GitHub项目跟踪 | 项目变化、适用场景、与当前工作的关联 | 从现有资讯/元数据能力延伸为主题研究；先进入知识，明确提出实践才建待办 |

这些能力可替代重复整理、检索、起草和部分验证工作；不能仅凭模型回答就认定业务已完成。发送消息、创建外部日程、发布和外部迁移需要相应授权与执行回执。

## 推荐技术结构

保持 TypeScript、React 和现有 Harness 模型/会话服务。无需另建模型配置系统，也无需先引入多 Agent 框架。

```text
任务 / 待回复 / 聊天指令 / 定时触发
  → 选择工作流模板与输入范围
  → 持久化 Job + Step
  → Host 执行已有工具，模型只负责理解、规划和生成
  → 保存 Artifact（产物）+ Evidence（来源/执行回执）
  → Agent 中心展示真实状态，业务服务按证据更新 Task / Reply
```

建议数据对象：

- `WorkflowDefinition`：类型、输入契约、允许工具、验收规则。
- `WorkflowJob`：事项ID、来源版本、工作区/账号、会话ID、状态、预算、去重键。
- `WorkflowStep`：输入摘要、执行状态、重试、检查点、工具回执和错误。
- `Artifact`：草稿、报告、文件或修改差异，关联来源和生成版本。

现有 jobs 可逐步扩展；runs 作为执行结果投影或历史记录兼容保留，避免两套状态都能任意修改。前端不能把“标记完成”当作真实执行器的完成信号。

同一事项优先复用会话，每轮只补新增证据；不同账号、项目或问题隔离。复用会话仍可能重复计费，长历史需要摘要检查点和可控轮换，不能无限累积。批处理按事项聚合，保留每条输入的独立结果和失败状态。

重试必须以工具副作用为边界：只读步骤可重试，本地写入用幂等键，外部写入须先核对回执；恢复只继续未完成步骤。输出验证包括结构、引用存在、版本未变、执行证据和人工修改保护。

调度需区分用户主动任务、最新消息与历史补采，给主动任务保留执行容量。批次按预算限流，避免大量历史识别阻塞回复草稿等交互请求；对模型校验失败展示具体原因、重试时间和可人工处理入口。

## 界面建议与实施顺序

Agent 中心保留顶部导航，主区域采用“待处理 / 执行中 / 待确认 / 已交付”。详情显示当前步骤、关联事项、依据、产物、耗时和用量，提供继续、取消与失败步骤重试。只有真实可关联的审批请求才显示批准入口；宿主接口不支持时明确跳回原会话，不展示虚假的审批状态。

1. 先修正台账/执行队列/审批的语义，打通现有 analysis、summary 作业的真实进度。
2. 接入批量回复和日报周报两个低副作用模板，验证暂停恢复、幂等、人工编辑保护和产物追溯。
3. 增加“处理此待办”，用限定工具的分步流程连接实际工作。
4. 最后扩展会议、研发及外部动作；按连接器实际能力逐项验收。

验收核心是“少了多少人工步骤、产物是否可用、失败是否可恢复”，而不是 Agent 角色数量。实现状态以办公执行实现记录为准，其余建议仍待逐项实施。
