# 消息识别与分流规则（2026-10-29 修订）

**发送格式补充：私聊回复只发送正文，不自动@对方或引用原消息；群聊继续引用原消息回复。用户手工输入的正文保持原样。**

本轮落实用户确认的完整规则，覆盖并替代《重点消息与日历接入》中“私聊已读移出待回复”的旧行为。识别入口继续使用现有重点采集、同账号批量模型会话和日历同步，不恢复全量聊天识别。

消息自动同步现按[工作时段调度](MESSAGE-WORK-HOURS-2026-10-29.md)：每天北京时间09:00–21:00，每5分钟一次。

## 判定表

| 来源 | AI识别 | 新建待办 | 待回复 |
| --- | --- | --- | --- |
| 私聊未读 | 是 | 明确具体处理事项才生成 | 同步时先登记“待AI识别”；判断为事项后退出待回复；需要答复则保留；无义务则移出 |
| 群聊@本人 | 是，不受已读标记限制 | AI确认实际处理义务后生成 | 有本人答复义务才登记 |
| 群聊@全员 | 是，不受已读标记限制 | 明确要求全员处理或参会才生成 | 明确要求反馈才登记；纯宣传、广播、知会不建档 |
| 群未读但未@本人/全员 | 是，仅判断沟通及已有关联事项 | **代码硬限制：不新建，包括普通群会议通知** | 有明确本人答复义务才登记；@他人的问题不属于本人 |
| 普通已读群聊、无@ | 不作常规识别 | 不生成 | 不新增 |
| 明确引用已有事项的后续消息 | 仅跟进对应记录 | 不新建；可以补来源 | 核对实际答复，禁止跨账号/会话关联 |
| 本人日历会议 | 明确日期地点直接同步，不让模型猜时间 | 沿用原会议ID；与唯一匹配的消息会议合并来源 | 不把未知邀请状态枚举猜成回复义务 |

具体处理包括开发、排查、登记、提交材料和参会；仅回答问题、确认或反馈进度属于沟通义务。**私聊同一条消息只选择一个路由，具体事项优先**。私聊中“处理完回复我”保留在任务描述内，不重复创建待回复。群内@交办并要求答复仍可分别记录两种义务。

## 状态更新

1. 私聊最新实际消息由本人发送：待回复标为已回复，记录原发送时间和消息证据。对方发来新一轮未读消息时，登记新的待识别项，保留原回复历史。
2. 已读只更新未读标记，不能自动关闭待回复。本人尚未实际答复时，既有回复义务继续保留。
3. 群聊只能由本人明确引用原消息的答复关闭对应待回复。同群无关发言、其他人的答复和群未读清零都不能关闭。
4. 聊天中的“完成了”“取消”等文本不再完成或取消已有待办。任务状态由实际执行结果或人工操作维护。
5. 日历自身的改期、明确取消仍更新会议。缺失、失败不推断取消；人工字段、归档及已完成状态受保护。
6. AI判断为事项/无义务时，旧待回复记录保留为“不需回复”，标记“已转待办”或“无需处理”，不删除历史，不伪造“已回复”。关闭自动建档时显示“待办待确认”，遵守原人工复核开关。
7. 人工明确标记的回复阶段、发送中的草稿、人工任务状态受保护；AI结果晚到时仍核对最新发言事实，避免已答复消息重新出现。

## 实现

- `src/shared/message-intake.ts`：新任务创建许可，群未读本身不能授予建待办权限；收件箱保存最新消息方向、ID和时间。
- `src/host/domain/reply-routing.ts`：私聊预登记、互斥分流、晚到结果核对；旧来源缺少会话类型时，仅从同账号已验证会话快照补齐。
- `src/host/integrations/yunzhijia.ts`：本地提交锁内分流，避免网络等待覆盖用户编辑；不向企业发送测试消息或改未读状态。
- `src/host/integrations/reply-reconciliation.ts`：最新实际答复核对，撤掉“私聊已读即不需回复”的旧分支。
- `src/host/analysis/message-analysis.ts`：模型规则、任务创建硬限制、私聊事项优先以及禁止聊天更新任务完成/取消状态。
- `src/host/analysis/rule-candidates.ts`：规则候选遵守同一建待办限制。
- 客户端：待回复展示“待AI识别”，历史展示转待办/无义务去向；原搜索、分页、回复草稿与真实发送流程保留。
