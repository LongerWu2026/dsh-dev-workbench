# Linky 研发任务接入设计

日期：2026-10-30；2026-10-31 补充本地开发工作区与 Linky 节点机制。本文件保留设计依据；当前代码、CLI 适配、验证结果及尚未实跑的业务环节以[研发任务实施记录](LINKY-DEVELOPMENT-IMPLEMENTATION-2026-10-31.md)为准。

## 结论与范围

将 Agent 中心改为「研发任务」，以 Linky 工作项为入口，让开发者查看本人需求、用户故事和缺陷，补齐上下文，启动真实的开发、测试、审查任务，并按业务流程交接。

Linky 保存业务事实和流转规则；Harness 保存本地执行过程、代码与测试证据。两者分别显示，避免将本地测试通过误写为业务验证或发布完成。

当前建议优先采用「Harness 执行」：通过 CLI 读取工作项，Harness 在绑定的仓库内执行，人工审查后按已验证的接口回写。「Linky 托管执行」作为独立模式：Linky 数字员工执行，工作台读取其运行记录。同一工作项同一轮执行只能选择一个执行方。

## 已验证的连接基础

- macOS 客户端自带 `linky 1.0.25`；官方入口为 `~/.linky/bin/linky`，指向客户端内的二进制。
- 已为本机现有 PATH 目录新增 `~/.local/bin/linky` 软链接；没有替换二进制或覆盖 shell 配置。
- 客户端认证位于 `desktop-linky.kingdee.com` profile。指定该 profile 后，`whoami` 与远端只读查询成功。
- CLI 无 profile 时的默认配置与客户端配置不同；连接器应显式传入用户选择的 profile，不能仅检测默认配置后判定未登录。
- 不复制 token 到工作台状态、前端、日志或仓库；CLI 继续管理认证。
- 认证探测使用 `whoami` 的实际返回与错误分类。仅根据进程退出码不足以判断登录成功；本次 `auth status` 的网络错误也返回过退出码 0。
- DNS、网络不可达与凭据失效分别报告，不能统一提示重新登录。

终端复核命令：

```sh
linky version
linky --profile desktop-linky.kingdee.com whoami
```

## CLI 能力与验证层级

| 能力 | 已核实的命令 | 本次验证 | 产品引入方式 |
| --- | --- | --- | --- |
| 本人需求、故事、缺陷 | `issue count`、`issue export`，`assignee_id:current_user` | 远端读取成功；导出 `complete=true`，计数与明细一致 | 主列表与自动同步 |
| 单据上下文 | `issue show` | 本人全部样本详情读取成功 | 描述、字段、父子关系、附件及产物索引 |
| 状态与可流转表单 | `issue statuses`、不带目标状态的 `issue move` | 读取成功；能区分可流转与 `no_transition` | 展示真实业务状态、候选动作与阻塞原因 |
| 研发模式 | `orchestration mode list` | 返回工作区现有模式 | 关联已有模式；不据模式名称臆造步骤 |
| 执行历史 | `issue runs`，`issue run-messages --since` | runs 查询成功，两个样本均为空；messages 仅核实帮助 | 有真实 run 后显示日志与增量进度 |
| 可用运行时 | `runtime list` | 查询成功，当前返回 Codex、Qoder、Claude | 显示实际在线状态；不宣称 Harness 已注册 |
| 流水线读取 | `pipeline list/status/logs` | list 查询成功，样本工作区返回空；status/logs 未有真实 run 验证 | 有关联流水线后再展示结果 |
| 分派与启动 | `issue assign`、`issue start` | 命令帮助已核实，未执行写入 | 后续受控接入；命令存在不等于有执行权限 |
| 产物回写 | `artifact create` | 帮助确认文件、仓库、分支、commit、MR URL 字段；未上传 | 回写设计、测试报告、审查报告和代码引用 |
| 业务流转 | 带目标状态的 `issue move`、任务内 `issue status` | 只核实契约，未变更状态 | 使用场景分别处理；不能互相替代 |
| 自动化测试 | `autotest task create/run/rerun/result/result-detail` | 帮助已核实，未调用测试平台 | 配置平台、产品、环境和任务后接入 |
| CI/CD 执行 | `pipeline trigger/cancel`、ERP 上报命令 | 帮助已核实，未触发 | 人工批准后的受控交付动作 |
| 知识与定时任务 | `knowledge`、`wiki`、`scheduled-task` | 命令目录已核实，未启用 | 后续扩展；不作为首期依赖 |
| 人工审核、外部执行器回调 | 尚未发现完整的审核通过/驳回、外部任务领取/完成命令 | 未验证 | 明确能力缺口，不能用产物状态或普通字段修改冒充 |

`issue create --help` 中存在过时的研发模式查询示例；本机实际可运行的是 `orchestration mode list`。实现必须结合当前版本帮助与实测结果，不直接照搬示例。

## 真实数据带来的设计约束

本次只读数据暴露出三类必须处理的情况：

1. 工作项只有标题、缺少描述/附件/产物，且关联父项返回不可见。此时先进入「待补充」，支持用户补充说明和选择可访问资料；不得仅凭标题自动实现。
2. 已验证通过的缺陷仍可能分配给本人。它应出现在业务历史中，不重新进入自动修复队列。
3. `status.category=done` 不等于交付成功。例如下版处理、已转故事、确认不处理均可能使用 done 分类。按工作区的状态 key、含义和实际流转关系建立策略，分别统计成功、延期、转交与不处理。

状态 `order` 仅用于展示顺序，不是流程顺序。当前可执行动作应以单据级 `issue move <id>` 的结果为准；能流转也不能证明业务验收已经通过。

## 页面设计

主导航将 Agent 中心调整为「研发任务」。首期保留简单列表与详情抽屉，避免另建大型流程编辑器。

- 顶部：Linky 连接状态、当前身份与工作区、最后成功同步时间；提供刷新和连接设置。
- 列表：待处理、执行中、待我审查、异常；另保留「显示全部」查看业务历史。异常和待补充显示明确原因。
- 每行：工作项编号、类型、标题、Linky 状态、本地执行步骤、下一位处理人、最近结果。
- 详情：原始工作项与引用资料、开发计划、执行记录、代码差异/MR、测试与审查证据。
- 操作按能力出现：补充上下文、绑定项目、分析、开始执行、暂停、重试失败步骤、打开 Linky、打开 MR。
- 业务状态和执行状态同时展示。例如「Linky：待处理；本地：等待验收标准」，不擅自将工作项改成阻塞。
- 人工登记的旧 runs 保留为历史记录，不加入新执行队列，也不作为审核或成功证据。现有办公作业继续可访问。
- 首期未接通审核回调时，提供原系统入口和刷新结果，不显示可以批准外部流程的虚假按钮。

## 本地开发工作区

支持用户先在本机建立「开发工作区」，指定已有代码工程，再将需求或缺陷绑定到该工作区。这里的开发工作区表示本机工程与执行环境，和 Linky 的团队工作区分开命名、保存与展示。

每个本地开发工作区配置：名称、主工程目录、允许引用的关联工程、基线分支、构建/测试命令、环境准备方式、默认编码执行器。路径通过用户选择的本地项目配置解析，不能接受缺陷描述中的路径作为执行授权。

一次开发任务的操作过程：

1. 选择 Linky 工作项，再选择已配置的本地开发工作区。
2. 展示本次工程、基线 commit、工作目录和执行方式。
3. 默认从选定的已提交基线创建独立 Git worktree 和任务分支，Agent 的工作目录固定到该 worktree。
4. 在任务页提供「打开 IDE」「查看差异」「运行测试」「查看日志」，代码实际保存在本机。
5. 人工审查通过后，按已授权范围提交、创建 MR 或将变更交回原工程。任务完成不自动删除工作区。

也可显式选择「使用现有工作目录」。该模式适合已有完整开发环境、希望人工与 Agent 共同修改的场景；运行前记录已有改动，同一目录内串行执行写任务，保护用户未提交内容。不能在原目录自动切分支、reset、clean 或 stash 用户改动。

新 worktree 不会自动包含原工程未提交的改动，也不会自动复制依赖目录、私有配置或测试数据库。任务需要基于在途修改时，应明确选择带入范围并记录基线；环境准备由工程配置完成。worktree 隔离代码目录，不隔离端口、共享数据库或外部服务。

一个工作区可配置多个工程引用，但每张任务要明确允许写入的工程；关联工程默认只读。Git 以外的工程不伪装成分支任务，先使用用户指定目录，直到另行配置可恢复的变更隔离方案。

## Linky 开发节点的已知机制

以下来自 2026-10-31 重新读取的官方操作手册和本机 `linky 1.0.25` 帮助；未启动真实开发节点，也未核实 daemon 内部 HTTP 回调协议。

1. **节点配置**：研发模式的一个步骤可以关联 Spec、产物模板、执行规范、执行智能体、验收标准、最大执行次数和人工审核。数字员工具有技能与指令，并绑定可用的 AI 运行时。
2. **启动步骤**：`issue start` 默认启动第一个 assigned 步骤，也能指定步骤名/序号；帮助说明其等价于界面 StartStepCard。
3. **本机执行**：`daemon start` 的帮助明确描述轮询任务并调用本地 Agent CLI，支持任务并发、超时和心跳配置。因此执行载体是绑定运行时所在机器上的编码工具。
4. **代码上下文**：手册第 6.4 节明确支持指定本地工作目录，也支持选择已配置代码仓库。`repo checkout <url>` 明确从 daemon 的裸仓库缓存建立 Git worktree。该命令的行为不能直接推广为「所有本地目录入口都自动创建 worktree」。
5. **交付与交接**：`artifact create` 可登记文档或代码引用（仓库、分支、commit、MR）；帮助明确下游步骤会通过 context bundle 接收这些产物。
6. **验收与继续**：手册描述失败时按最大执行次数重试，超限转人工；启用人工审核后需人工确认才继续。公开说明中的验收项包括是否存在产物、产物名称、交接摘要关键词，这些检查不能代替编译、测试与代码审查。

Harness 方案沿用「工作项 + 本地开发工作区 + 可恢复执行 + 交付证据」这一结构，开发步骤可以直接由 Harness 在选定工程中执行。将 Harness 注册成 Linky 原生运行时仍需另行验证平台适配协议，两条执行路线不能同时修改同一任务。

## Harness 执行流程

```text
同步本人工作项
  → 判断工作范围、业务状态与执行归属
  → 准备检查：描述、验收标准、上下文、仓库、基线、测试命令
  → 自动分析与计划
  → 在隔离 worktree 中开发/修复
  → 运行真实测试与必要的复现验证
  → 独立审查会话检查 diff、需求符合性与测试覆盖
  → 有问题则有限次返修；超限暂停并说明
  → 人工审查具体 commit 与证据
  → 批准后按团队策略提交/合并、提测和回写
  → 读取测试验证与发布结果，等待或推进后续授权步骤
```

需求开发需增加需求澄清、验收标准和设计审查。缺陷修复需增加复现、根因与回归范围。不同工作项适用不同模板，不能共用一段笼统提示词。

人工审查绑定 `repo + base commit + head commit + artifact digest`。任意代码变化后原批准失效；独立 AI 审查不是人工批准。GitLab/GitHub 的 MR 审查状态需要对应连接器或正式接口，Linky 的 `--mr-url` 只保存引用。

发布、迁移和删除仍需按用户约定单独确认；不把一次开发批准扩展为所有后续动作授权。

## 状态流转契约

- 外部开发者工作台使用 `issue move` 的单据表单契约，保留权限、前置条件、必填字段、说明和流转记录。
- 数字员工任务环境使用 Linky 给定的任务协议；CLI 明确拒绝在 `LINKY_AGENT_ID` 环境中用 `issue move` 执行目标状态。不得通过清除环境变量规避限制。
- `issue status` 不能在外部工作台中替代带表单与记录的流转；不能为了自动化便利绕过审批。
- 每次写入前重读当前状态、处理人和输入版本。变更请求超时后先查回执/历史，不能盲目重复上传、评论、启动或流转。
- 普通状态字段变成「评审完成」不自动证明某个 commit 已获人工审查。必须有可关联的批准来源、批准人和代码版本。
- `artifact --status approved` 是产物状态，不是人类审核动作或权限凭据。

## 自动接收与恢复

建议在用户启用后按可配置间隔同步已选工作区本人工作项。当前核实的是分页查询能力，未发现可直接使用的 Webhook 订阅契约，因此首期使用轮询，不宣称实时事件接入。

- 同步作业与开发作业分开；不能沿用消息识别「每批 50 条」作为同时启动 50 个编码任务的规则。
- 默认只运行一个会修改同一仓库的任务；不同 worktree 也需防止共用测试环境、端口或数据库冲突。
- 活跃作业持续跟踪原工作项 ID；工作项转交他人后即使从「我名下」列表消失，也应暂停待确认而非误判删除或成功。
- 以 server、profile/account、workspace、issue ID 标识业务对象；执行另有稳定 run ID 和输入指纹。普通评论更新时间不触发新一轮重复修复。
- 部分导出失败或 `complete=false` 时保留旧快照并标记不完整，不用缺失行推断删除，不把导出条数当总量。
- 在途步骤有 lease/执行标识；重启时区分确定未执行、执行成功、结果未知。代码提交、上传和外部流转必须先恢复回执。
- CLI 版本变化后重做能力探测；401、无权限、网络失败、必填项不满足、仓库冲突分别显示恢复办法。
- 电脑睡眠或 Harness 未运行时无法保证持续接收；长期无人值守需要常驻运行环境。

## 分期交付与验收

1. **接入与准备检查**：真实本人工作项列表、详情、状态、原单跳转、项目映射和待补充原因。验收包括 profile 区分、网络/认证错误、完整性、跨工作区字段、去重及已完成项排除。
2. **单条开发闭环**：挑选一张上下文完整且获准执行的单据；分析、隔离开发、测试、独立审查、人工驳回返修和批准。验收必须有真实 diff、测试退出码、commit、批准记录；代码改变后批准失效。
3. **回写与持续接单**：在指定试点单上验证产物、流转、MR/CI，以及重启、超时不确定回执、转交他人、重复触发和失败恢复。通过后启用有限范围自动接收。
4. **原生 Linky 托管**：平台确认外部执行器注册、任务领取、心跳、结果回调、取消和人工审查事件后，再决定是否将 Harness 注册为运行时。缺少这些契约时只做外部开发者执行与结果联动。

实现后运行 `pnpm build`、`pnpm check`、`pnpm test`，按界面改动补充有意义的布局验证；另安排授权试点的端到端验收。模拟测试不能替代平台写入、人工审核回调和真实 CI 的验收。

## 证据边界

本轮仅新增本机 CLI PATH 入口、读取远端数据、编写设计和本地验收报告；未改生产业务代码、未启动数字员工或流水线、未提交或流转工作项。个人明细与原始响应保存在 Git 忽略的 `.tmp/linky-intake-20261030/`，不放入发布包或公共仓库。
